# Agent large-artifact protocol

Status: repository-level operating protocol for reviewers, coding agents, and scientific agents.

## Purpose

Large experiment artifacts, logs, JSON traces, and evaluation outputs are audit data, not conversational context.

Agents MUST NOT stream large claim-bearing artifacts into an LLM context when the same task can be completed by local parsing plus a compact validated summary.

The default architecture is:

```text
full claim-bearing artifact
        ↓
local deterministic parser / independent validator
        ↓
bounded reviewer summary
        ↓
LLM review / coding work
```

The full artifact remains authoritative. The summary is derivative-only unless a specific contract explicitly promotes it.

## Size thresholds

Treat the following as large by default:

- JSON, JSONL, CSV, logs, traces, or other text artifacts larger than ~1 MiB;
- any file that causes connector/tool output truncation;
- any file with long per-update, per-token, per-example, or per-step traces;
- any artifact that would consume a material fraction of the agent context window if printed.

For reviewer-facing summaries, prefer a hard size cap. For the A2 gradient-clipping experiment the cap is 64 KiB.

A size cap MUST fail closed if the summary grows beyond the bound.

## Required workflow

### 1. Preserve the full artifact

Do not delete, rewrite, compress away, or retroactively modify sealed claim-bearing evidence merely to make it easier for an agent to read.

If evidence is already sealed/published, its bytes, manifest hashes, archive hashes, request IDs, run IDs, and provenance remain immutable.

Do not rerun a consumed scientific execution merely to obtain a smaller representation.

### 2. Materialize once

When raw inspection is necessary, materialize/download the large artifact locally once.

Do not repeatedly fetch the same multi-megabyte file through GitHub/connector/chat APIs.

Do not `cat` the entire file into terminal/chat output.

### 3. Parse locally

Use a deterministic local parser, script, or validator to extract only the fields needed for the current decision.

Examples:

- per-seed rescue events;
- paired contrasts;
- intervention counts;
- aggregate norms;
- hashes and provenance identities;
- validation status;
- selected failure records.

Do not print full per-update traces unless a specific defect requires a narrowly bounded slice.

When memory is constrained, prefer streaming parsing over loading the entire artifact.

### 4. Produce a bounded derivative summary

The summary should normally contain:

- summary format/version;
- explicit `derivative_only` marker;
- path/identity of the claim-bearing artifact;
- implementation/source identity;
- relevant validation/provenance state;
- compact per-arm/per-seed outcomes;
- aggregate/paired metrics required by the reviewer;
- hashes/commitments required to bind summary fields to full evidence;
- explicit held-out/generalization boundary where applicable;
- explicit scientific-scope markers such as `GO_LATENT = NOT EVALUATED`.

The summary MUST exclude bulky raw projections/traces when a hash or compact metric is sufficient for normal review.

### 5. Bind the summary to full evidence

A producer-generated summary alone is not enough for scientific acceptance.

At least one of the following must hold:

1. an independent validator deterministically reconstructs the summary from the full claim-bearing artifact and requires exact equality; or
2. the summary is generated by the independent validator itself after full evidence validation.

For byte-stable formats, exact byte equality is preferred.

A summary hash that is merely recomputed from producer-owned summary fields is only a self-consistency check and is not an independent binding.

### 6. Review the summary first

Reviewers and coding agents should use the compact summary as the default read path.

Only descend into the full artifact when:

- the summary indicates a contradiction or anomaly;
- a claim cannot be decided from compact evidence;
- an adversarial validation question requires raw trace inspection;
- a suspected implementation defect requires a bounded local slice.

When descending, extract only the relevant slice locally and return the compact result to the LLM context.

## A2 gradient-clipping implementation

The A2 gradient-clipping experiment currently uses:

- full claim-bearing evidence: `producer-evidence/a2-gradient-clipping.json`;
- bounded derivative summary: `a2-gradient-clipping-review-summary.json`;
- summary version: `a2-gradient-clipping-review-summary/1.0`;
- hard summary cap: 64 KiB.

The summary retains reviewer-relevant information such as:

- rescue events and persistence;
- clipping summaries;
- cross-seed aggregates;
- paired causal contrasts;
- intervention consistency;
- control-equivalence hashes and final identities;
- gradient evidence commitments;
- source/canonical identities;
- held-out boundary;
- `GO_LATENT` scope.

It intentionally excludes the huge raw `reference_projection` and full per-update traces.

For new executions, `scripts/run_a2_gradient_clipping.py` writes and validates the compact summary next to `producer-evidence/`.

For already existing sealed evidence, use an explicit derivative output path outside the sealed evidence root and pass the accepted implementation commit:

```bash
python -m scripts.build_a2_gradient_clipping_review_summary \
  --producer-output-dir <sealed-evidence-root>/producer-evidence \
  --implementation-commit <accepted-implementation-commit> \
  --summary-output <path-outside-sealed-evidence-root>/a2-gradient-clipping-review-summary.json
```

The offline extractor first runs the independent persisted-evidence validator against the accepted implementation commit and source identity. Only after that validation succeeds does it derive the compact summary. The output path is rejected if it is inside the sealed evidence root, so the source evidence bytes/tree remain unchanged.

## Forbidden patterns

Agents MUST NOT use the following as the normal workflow:

```text
GitHub fetch large JSON
→ receive truncated response
→ fetch/search the same file again
→ reason over partial output
```

Also avoid:

- pasting multi-megabyte logs into chat;
- printing entire model traces;
- repeatedly polling the same large artifact;
- treating truncation as evidence completeness;
- rebuilding scientific evidence by hand from partial connector snippets;
- rerunning science simply because the artifact is inconvenient to inspect;
- editing sealed evidence in place to make it smaller.

## CI and logs

The same principle applies to CI.

For successful jobs, prefer status + compact test counts rather than full logs.

For failures:

1. identify the first real failing job/step;
2. fetch only the relevant failure log if necessary;
3. quote/return only the relevant traceback or bounded context;
4. do not dump the full CI log into the conversation.

Do not aggressively poll long-running CI/scientific jobs in tight loops. Record the run ID and check terminal state at reasonable intervals or in a later turn.

## Reviewer workflow

Reviewer owns:

- provenance ledger;
- consumed run/request IDs;
- scientific interpretation;
- decision whether raw evidence inspection is necessary.

Reviewer should reason primarily over independently bound summaries, not raw megabyte-scale traces.

A reviewer must not weaken evidence contracts merely to reduce artifact size.

## Coding-agent workflow

Coding agents should:

- read this file at the start of artifact-heavy tasks;
- keep large data outside the conversational context;
- write small local parsers when needed;
- report compact findings only;
- preserve scientific/evidence semantics unless explicitly tasked to change them.

A coding agent must not substitute a hand-written summary for validator-bound evidence.

## Prompt rule for new chats

New reviewer/coding-agent prompts should reference this file instead of reproducing the entire protocol.

Recommended mandatory line:

```text
Before handling any artifact/log/evidence, read and obey `docs/AGENT_LARGE_ARTIFACT_PROTOCOL.md`. Large artifacts stay outside LLM context; use local parsing and validator-bound bounded summaries.
```

If the repository version of this file is unavailable in a new environment, the orchestrator may inline a short fallback containing these four invariants:

1. do not stream >~1 MiB artifacts into LLM context;
2. materialize once and parse locally;
3. use a bounded derivative summary independently bound to full evidence;
4. never modify/rerun sealed evidence merely for readability.

## One-chat/one-round companion rule

Large-artifact discipline does not solve context degradation by itself.

For coding agents, prefer one chat per implementation/repair round. After commit + fresh natural CI, stop for external review.

For reviewers, keep one chat per coherent lifecycle/scientific phase and start a new reviewer chat after major stage transitions when the accumulated context is no longer needed.

The goal is to keep both data volume and decision history bounded without sacrificing provenance or auditability.
